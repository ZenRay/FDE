# Week01 学习成果检验

更新日期：2026-11-03

这份文件用来回答“我今天真的学会了吗”。它对应[Week01 六天学习安排](Week01学习安排.md)，是个人自检工具；正式作业仍以[W01 作业任务书](<../../projects/W01 材料包 20261023/W01/05_作业任务书.md>)和工程契约为准。下面的例子帮助你判断回答质量，不是青禾优选的标准答案，也不表示你已完成任何访谈或产品运行。

## 怎样给自己判定

每个问题先**不看课件，用自己的话或一份实际记录回答**，再对照“达到标准”。状态只用三种：

| 状态 | 什么时候填写 |
| --- | --- |
| 已达到 | 能独立解释，并拿得出对应的材料位置、代码位置或自己的运行记录；涉及动手的项目确实在本机完成 |
| 部分达到 | 理解了思路，但还依赖提示、缺关键证据、只读了代码尚未运行，或答案没有说到如何重新判断 |
| 待验证 | 尚未练习，或正式访谈、模型服务等必要条件仍未具备 |

不要把“课件这么说”“README 给了预期名单”“老师演示成功”写成“我本机已验证”。概念理解和技术实测可以分别标状态。例如能解释 S03 为何不能算零，但还没有运行自己的模型，概念项可记已达到，实测项仍是待验证。每次记录证据位置及一句“这份证据能支持到哪里”。

## 第一天｜客户事件与角色

**今天要学会：**把沈总邮件当作项目起点来读，分清客户期待、客户解释、已有材料事实和待核实条件；知道客户内部与产品方各要作什么决定。

**自测 1：沈总说“会员老化比较明显”，你现在能写下哪两种不同的结论？**

达到标准的回答应分别写出：第一，邮件证明沈总提出了这个解释，能定位到邮件位置；第二，“会员老化造成复购下降”尚无充分依据，要进一步核实会员分组、时间范围、复购口径和其他可能原因。把这句话直接写成“已确认的根因”不算达到。反过来，连“沈总提出了这个判断”也一概写未知，同样没有充分利用现有材料。

**自测 2：如果老周说可以导出订单，你会找谁、要什么、接着决定什么？**

回答应提到数据字段及口径、覆盖时间、会员身份对应、可否获准用于验证等具体问题。老周的表态可以成为联系和核查依据，尚不能替代获准样本和实际导入。答案若只写“找 IT 沟通数据”，缺少材料与用途，仍属部分达到。

**自测 3：客户愿意试演示，能直接安排正式部署吗？**

用 V02 第 12 页图书馆案例回答。应说出目前可以继续演示或核查的范围，以及预算、资料访问许可、投入决定等尚缺条件；说明获得哪些确认后才改变安排。把演示、采购批准、交付启动连成自动发生的一步，不算达到。

**自测 4：这个项目有哪两项不同的投入决定？**

说清客户内部立项要比较业务问题、责任、收益成本风险和预算；产品方投入要比较产品适配、验证资源与阶段前提。举出一个“客户有意愿但产品方还不该承诺”的情况，以及一个“产品可演示但客户仍未批准投入”的情况。只背两个名词，没有说出各自决策依据，仍属部分达到。

**当天证据：**邮件摘录与位置、角色关系图、两项决定的状态记录、独立完成的图书馆练习和青禾接手说明。W01 只开放沈总访谈，其他角色的意见不能凭协作表推断出来。

## 第二天｜立项四问与产品适配

**今天要学会：**从具体工作出发，用产品证据和开始条件推导下一阶段；遇到新证据时修订判断。

**自测 1：客户 A 说“希望 AI 减少回访准备工作”，要观察什么？**

回答应包括人工原先怎样比较消费和整理名单，系统打算辅助哪一步，运营仍要审核修改和安排回访。比较总准备耗时要包含审核、修改、返工，还要看名单是否准确。回访后的业务效果另行验证。只统计模型生成用了几秒，或把“准备时间减少”写成“复购一定改善”，都不算达到。

**自测 2：四问怎样连起来，而不是四个独立填空？**

请用练习 A 讲一遍：第一问确定要改善哪项工作；第二问核对产品已有能力和客户差异；第三问明确数据、使用者、口径责任和投入条件；第四问据前三问决定先核查、带条件验证，还是暂缓某个阶段。回答第四问时要指明**阶段**。只写“建议继续推进、风险可控”没有下一步对象和条件，仍属部分达到。

**自测 3：写一条能被复核的 fit-gap 记录。**

可用 V03 的练习 A：若 IT 只是表示可以导出订单，可以初步考虑“系统适配”，将这个表态标为 reported，并关联产品数据能力；下一步要取得获准的脱敏样本和字段说明，核查口径、覆盖、身份映射和访问条件。这里的分类表示预计怎样处理，reported 表示目前证据有多强，两者不能合并。“系统适配”不等于适配已完成。

换成青禾时，用自己的材料和运行来源重新写。若尚不能确定处理方式，写“待判断”并给出核实路径；“暂不承诺”则说明当前不承诺的具体交付或效果。把所有条目一律填未知、待判断，也不算认真使用了已知能力依据。

**自测 4：同一个练习 A，条件改变后下一步怎样变？**

| 新情况 | 达到标准的下一步 |
| --- | --- |
| 样本获准、口径有人负责、走查和探索投入已安排 | 进入有范围的样本验证，比较名单质量、审核修改量和总耗时；仍不保证业务效果 |
| 有样本，但哪些会员纳入分析存在冲突，没人负责确认 | 先确定确认责任人和范围，再安排验证 |
| 没有可用样本和使用者，却要求保证业务效果 | 暂缓该客户样本验证和效果承诺；取得样本与参与者后重新评估 |

每个答案还要说出“我用了什么依据、什么变化会再次改变决定”。把三个情境都回答成“继续调研”不算达到。练习 A 的样本验证是该案例的阶段建议，不自动成为青禾的决定。

**当天证据：**客户 A 的四问及一条适配练习，青禾独立工作稿，三情境的先答后改记录。产品能力若只来自课件或代码，明确标成“待本机验证”。

## 第三天｜Agent 执行机制与受控动作

**今天要学会：**把一次 Agent 回答拆成模型、程序校验、业务计算、状态保存和外部动作几个责任位置；能够沿代码和实际记录走一遍。

**自测 1：用户明确要求比较 2026 年 7、8 月消费，名单和金额从哪里来？**

请画出：用户输入→模型选择工具并传参数→程序检查工具和日期→Business.compare 查询并计算→工具结果回到模型→最终回答。能说明净消费按支付减退款、取消订单不计，模型提出建议但不应自编金额。样例名单 M001、M004、M007 可用于核对，实际运行时还要检查本次工具结果。仅复述最终名单，没有追到计算与证据，不算达到。

**自测 2：下面三种情况为什么不同？**

- M004 在完整覆盖的时段没有订单：可以是实际消费为零。
- M005 的基期净消费为零：下降比例没有定义，不能把它当 0% 或 100%。
- S03 缺少 8 月覆盖：消费未知，不能把未知写成零，也不能据此生成该门店的下降名单。

应能指出业务数据与覆盖检查的位置。把“空结果”统一解释成“没有下降会员”，仍属部分达到。

**自测 3：三个工具请求会在哪一层被拦？**

V04 第 18 页给了三类练习。缺必填日期字段先看 schema；不存在的日期如 2026-02-31 要过业务日期校验；只读入口中即使用户说“我批准了”，也没有主机授予的动作权限。能解释前一层通过不意味着后一层也通过，才算达到。只说“系统会拒绝”但不知道原因和检查位置，仍属部分达到。

**自测 4：标签动作中，checkpoint、账本和服务端各管什么？**

checkpoint 让会话能从中断处继续；动作账本保存草案、确认、执行或未知状态；独立标签服务保存外部实际状态。一次确认要绑定当前草案、会话和内容哈希。修改会员或标签，应作废旧草案并重新确认。HTTP 超时先用原 ID 查询；一次 404 也不证明仍在途的写请求一定不会生效。若后续动作改过标签，撤销需要防止覆盖后来的状态。

能用自己在教学 Mock 的一次草案、确认、查询、撤销记录核对实际状态，才把“动作闭环已实测”标为已达到；只看代码可标机制理解。回答“LangGraph 有 checkpoint，所以外部动作必然恰好执行一次”不算达到。

**当天证据：**两类请求路径图、三输入练习、标签状态与查询记录、客户扩展位置图。客户语义、连接器、评估与通用产品补丁各有不同位置；松果样例能运行不证明青禾已接入。

## 第四天｜运行记录、故障定位与评估

**今天要学会：**建立可比较的真实模型基线，找出一次失败最早发生在哪一层，并提出能复测的改动假设。

**自测 1：为什么一次“成功回答”还不足以作为基线？**

回答应包含模型及协议、产品和数据语义版本、提示词或其哈希、原始任务、工具与最终输出、trace。成功和失败都要保留。若前后同时换模型、数据和提示词，就不能把结果变化明确归因到某一项。README 的预期结果或教师历史报告不是自己的基线。

**自测 2：S03 的运行返回 incomplete，应该怎样查？**

从同一 trace ID 依次检查输入时间、模型请求、compare_spending 的参数、工具返回的 partial 与缺覆盖门店、最终输出校验。指出首次出现“信息不足”的位置，再说明模型是否承认了限制、程序是否改判了状态。只看最后一句“未完成”就断定模型行为正确，证据还不够。

**自测 3：工具结果正确，最终 JSON 却不能解析，先改哪里？**

先归到输出格式或运行机制层，检查模型返回和有限修复流程；不要因最终失败就修改正确的 SQL 计算。反过来，若业务函数本身返回错误日期或覆盖，应先解决数据或工具层。评估脚本抛 JavaScript 语法错误时，先确认测量工具能运行，再解释模型分数。回答“所有失败都是 prompt 不够好”不算达到。

**自测 4：写一个可以验证的改动假设。**

用“缺时段时模型仍先请求消费比较”为例，可以假设工具说明或澄清规则表达不清。先固定模型、数据和用户输入，只调整一处，比较被拦下的调用次数、澄清内容与耗时，再回归明确日期分析、S03 缺覆盖和只读拒绝。若没有实际做前后对照，把它写成“后续假设”；不能写“已提升”。

**自测 5：怎样读 Promptfoo 报告？**

分别检查评估框架是否完成、各用例断言是否通过、原始回答是否有正确依据。正常分析、缺时段澄清、只读约束只是基础覆盖；缺覆盖场景由产品验证另行检查。通过率不能替代建议价值、自然语言因果判断和安全失败的人工复核。若评估脚本自身失败，它要单独修复和记录。

**当天证据：**自己的真实模型运行基线、场景文件与 trace、一次分层诊断、评估报告和假设记录。若模型服务未打通，就保留脱敏错误及下一步，真实运行项维持待验证；可以继续完成机制练习。

## 第五天｜案例迁移、沈总访谈与初步 fit-gap

**今天要学会：**从案例学习怎样拆解人的具体工作和交付责任，再用青禾自己的证据做初步适配判断。

**自测 1：Assistant 与 Debrief 都帮助顾问，为什么还要分开分析？**

Assistant 主要支持内部知识查找与归纳；Debrief 进入会议记录和会后跟进。后者要讨论客户同意、要点与行动项、CRM 中的记录、邮件草稿由顾问编辑并决定发送。应能把“内容可用”“工作按约完成”“工作是否改善”分开提问。公开披露事实与教师提出的访谈、阶段建议也要分别标明；不能把教师模拟写成企业当年的原始决策。

**自测 2：假如新客户要求自动发送邮件，交付范围多了什么？**

应写出发送条件、授权、人工确认位置、失败及错发处理责任，还要考虑怎样核对实际发送状态。只在功能表增加一行“自动发送”，却沿用草稿阶段的检查方法，仍属部分达到。迁移青禾时只能借这种拆法，不能借 Morgan Stanley 的 CRM 接入或效果结论。

**自测 3：沈总正式访谈前，你会怎样选问题？**

从邮件已知和四问缺口出发，优先确认效果定义、会员老化的依据、运营要改变的工作、数据与投入条件。每个问题后面写“回答会影响哪个判断”，避免机械询问全部角色事项。本周只开放沈总；老周、小林、陈姐、王经理可以是后续核实对象，不能被写成已访谈。

**自测 4：正式访谈后，记录能否让别人追溯？**

保留原始问答或导出消息 ID，分开写客户原话、你的解释、目前核实程度、冲突与未知，再指出下一步找谁、取什么资料。若入口未开放，这项就是待验证；课件回放和虚构对话不能补上。对初步 fit-gap，分类与证据状态分开，未知有核实路径，不为了填满表格而制造五类条目。

**当天证据：**案例事实与教师分析表、带决策用途的访谈提纲、真实访谈记录或待开放状态、fit-gap 工作稿及立项建议草稿。

## 第六天｜共创案例对照与 W01 交付

**今天要学会：**看清不同项目起点会改变下一步投入，并把 W01 的客户证据、技术运行和交付文件连成一条可复核的链。

**自测 1：V08 中为什么两个客户没有走相同的下一步？**

有投手团队的服装客户可以进一步探索投手 Copilot 的工作切口；获客基础尚未建立的制造企业，短期 AI 试点难以隔离基础业务问题，课件选择暂不进入该范围试点。回答应说明该判断针对**哪一阶段**，不是给客户贴永久标签。V08 从产品尚在共创出发；青禾则要先核查已有标准产品与客户要求的适配。

**自测 2：V08 的哪些话只能写成计划或约定？**

后来讨论的成本承担、优惠和合作安排不能被写成最初已具备；约定的能力验收不等于已经验收；“计划观察投手工作”不等于已经完成观察。还要把三种证据分开：能力是否达到约定、效率是否变化、广告业务效果是否变化。将这种时间与证据的区分带回青禾报告。

**自测 3：青禾的阶段建议能否顺着前三问读下来？**

读者应能从客户问题和使用工作，找到标准产品已验证的能力，再看到客户口径、数据、角色与决策上的缺口，最后理解你建议进入哪个阶段。写清开始条件、投入范围、检查点、调整或暂缓的触发情形，以及暂时不承诺什么。仅写“带条件继续，建议先试点”没有这些内容，不算达到。

**自测 4：五份正式文件能否相互印证？**

工程内需要四份 JSON：environment_check、model_baseline、runtime_evidence、product_fit_gap；另有立项报告 project_assessment.md。检查同一产品版本、各自契约版本、能力 ID、证据文件路径与 SHA-256。environment_check 的九项状态应来自实际检查；完整技术就绪要求九项均 pass 且模式为 live。model_baseline 至少保留四次场景运行；runtime_evidence 记录规定的七类行为、文件路径与哈希。访谈证据与产品证据各支持各自的判断。

**自测 5：通过公开 checker 后，还需要看什么？**

checker 能检查结构、版本、部分状态与哈希；它不能证明你真的完成了访谈、自然语言建议合理，或青禾复购能改善。继续人工检查多轮日期选择、拒绝旧草案、退款解释、HTTP 动作真实状态，以及报告中的客户承诺。Promptfoo 真报告应与本次模型基线一致，并由 finalize_evaluation.py 补齐环境评估状态。提交 zip 的顶层路径为 artifacts/、docs/ 等，所引用的证据文件一起进入包，运行态与密钥不进入包。

**当天证据：**V08 与青禾的起点对照、修订后的四问与报告、四份 JSON 和引用证据、Promptfoo 报告、checker 输出及人工复核记录、提交包清单。条件受阻时写真实缺项和补齐方式，不因空模板齐全就标完成。

## 整周结束时再看两条门槛

**技术门槛**看的是自己的真实模型、业务工具、样例数据和标签 API 有没有形成可重跑的行为证据，契约文件及评估是否完整。**交付门槛**看的是能否区分客户诉求与已核事实、逐项说明适配和未知、提出必要核查对象，并守住阶段与效果承诺边界。两条分别判断；代码写得多、报告写得长，都不能抵消另一条缺项。
