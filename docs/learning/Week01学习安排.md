# Week01 六天学习安排

更新日期：2026-11-03

这份安排写给第一次接触 FDE 项目的人。读完课件后，你要能把一封客户邮件、一套可运行的 Agent 产品和一次立项决定连起来。下面的“天”表示六个连续的学习单元，不规定每天必须花多少小时；遇到模型接入或访谈入口问题，就保留真实进度并把未完成的动手部分顺延。每天的学习目标与检验办法单独放在[Week01 学习成果检验](Week01学习成果检验.md)。

## 先看懂这周的故事

青禾优选希望改善会员复购下滑，沈总提出了“会员老化”“80 万活跃会员”“三个月看到效果”等说法。你代表产品方的 FDE，手里有一套标准会员运营 Agent，但它运行的是另一家虚构公司的样例数据。你需要先弄清客户想改变哪项工作，再核实产品做得到什么、接入客户数据还缺什么，最后建议下一阶段投入到哪里。

FDE 在这里是连接业务问题、产品实现和现场反馈的人。你需要读懂客户的工作，也需要能从代码和运行记录里找到产品能力的依据。第一周的重点是“形成有证据的进场判断”，不是替客户提前实现所有功能或保证复购结果。

初读课件时，先把几个词按用途理解，不必背定义：

| 课件中的词 | 在本周可以怎样理解 |
| --- | --- |
| 2B 项目 | 产品方与一家企业协作；使用者、提供数据的人、批准预算的人可能不是同一人 |
| Agent 与工具 | 模型判断下一步要问什么、调用什么工具；工具在程序约束下查询或执行，计算和权限不能只听模型的一句话 |
| Mock | 用于教学的独立模拟服务，有自己的接口和状态；适合练习标签动作，但没有接入青禾生产系统 |
| fit-gap | 逐项记下客户要求与标准产品能力之间的适配和差距，附上判断依据与下一步 |
| trace 与基线 | trace 记录一次运行经过哪些步骤；基线把模型、产品、数据、输入和结果一起固定，便于后来比较 |
| 契约与 JSON Schema | 交付文件必须遵守的字段和格式规则；文件格式合格仍需要核对实际行为和业务判断 |

这周会不断遇到三个不同对象：

| 对象 | 在学习中用来做什么 | 使用它时的提醒 |
| --- | --- | --- |
| 青禾优选 | 本周要形成判断的客户沙盘 | 客户事实只来自这套材料、你自己的正式访谈和后续客户验证 |
| 松果生活 | 标准产品自带的独立样例 | 可以核查产品的计算、对话和受控动作，不能推算青禾会员数或复购率 |
| 课堂案例 | V03 的客户 A、V06 的 Morgan Stanley、V08 的投手 Copilot | 借鉴分析方法；案例人物、系统和结论不移植到青禾 |

你还会用到两个系统：学员运行和后续适配的标准 Agent 产品，以及课程提供的 AI 客户访谈系统。前者用于产品验证，后者用于正式访谈与保存记录。它们的状态和证据不能互相代替。

## 第一天｜把一封邮件读成一个待核实的客户事件

先读沈总邮件，再读 V02 第 1–4 页。不要急于列功能清单，先问：沈总为什么现在提这件事？他期待的结果、提出的原因解释和希望改变的日常工作，各是什么？

以“会员老化比较明显”为例。邮件足以证明**沈总这样判断**，但还不能证明会员老化造成复购下降。要讨论原因，你可能需要先知道“老会员”如何定义、各时间段的人群怎样变化、复购率怎样计算，是否还存在商品、渠道或运营动作的其他解释。“三个月看到效果”也是一个期望；若还不知道“效果”指什么，它就不能直接变成产品方承诺。

把邮件中的关键说法写成下面的格式，并标明邮件段落或来源标识：

| 客户原话 | 当前可以怎样理解 | 还需要什么依据 |
| --- | --- | --- |
| “80 万活跃会员” | 发起人提供了一个规模说法 | 活跃定义、统计时间、去重方法、可用数据范围 |
| “别又让她多整理一套表” | 发起人关注小林的工作负担 | 小林现在怎样整理，助手结果要进入哪一步 |

接着读 V02 第 5–8 页和协作关系材料。画一张“问题找谁”的小图：沈总解释目标与推进条件，老周核实系统和数据，小林描述运营流程，陈姐说明门店能否承接，王经理说明预算合同。再把产品方销售、售前、解决方案、实施、CSM 和 FDE 放进图里，想想谁负责澄清需求、谁推进商务、谁把现场限制带回实现与交付。一个人出现在名单上，只表示你知道该找谁，尚不表示他已经授权或承诺。

读 V02 第 9–11 页时，把两项决定分开写。**客户内部立项**要考虑问题值不值得投入、谁负责、预算和审批怎样安排；**产品方投入判断**要考虑产品是否适合、验证需要多少资源、从什么条件开始。客户愿意演示并不自动进入采购，产品方愿意验证也不代表双方约定了交付范围。采购中的方案评估、商务比较、审批和启动，具体先后以客户实际流程为准。

最后先独立做 V02 第 12 页的图书馆练习：业务负责人愿意安排知识助手演示，但预算未定、资料访问待批。写下目前能开展的交流、正式部署前还需要什么、谁能确认。再看课件解析。第 13 页帮助你区分学员产品和 AI 客户系统。

当天把邮件拆解、角色图、两项决定和图书馆练习合在一份工作稿里。以一段给新同事看的接手说明收尾：我们知道什么、还不知道什么、先核实哪件事、核实结果会改变什么决定。暂时不知道的事可以保留，不需要编出答案。

## 第二天｜把“想做 AI”变成可以讨论的下一阶段

读 V03 第 1–4 页，先用课件里的**独立客户 A**练习，不要把它当青禾资料。客户 A 的运营每月要人工比较消费、整理回访名单和建议。系统可以辅助比较、列依据、起草建议；运营仍要审核修改并安排回访。这时“减少准备工作”具体指什么？应比较同一类任务的总准备耗时，包括核对和返工，还要检查名单质量。至于回访后的业务效果，要另外观察，不能从生成速度直接推出来。

拿出[四问工作表](<../../projects/W01 材料包 20261023/W01/04_立项四问与访谈提纲.md>)。四问是一条推理链：**客户要解决的工作问题→标准产品为什么可能适用、边界在哪里→下一阶段的开始条件→现在投入到哪个阶段**。前三问给第四问提供依据。先替客户 A 写一版，再另开一栏写青禾目前能回答到哪里，避免把练习 A 的运营表态当成青禾访谈结果。

读 V03 第 5–10 页，打开能力矩阵和 API 说明，学习把一句需求拆成几项可以单独判断的工作：消费比较、下降筛选、名单依据、客户订单接入、可供人工修改的建议、实际回访安排。产品自带的“老会员”“净消费”“下降至少 20%”有明确规则；客户是否采用相同规则，需要向客户核实。一个功能在松果样例上跑通，也只说明样例条件下的行为。

这里要理解 fit-gap：它是一张**客户要求与现有产品能力的差异记录**，每条写明来源、相关能力、初步处理方式、证据强弱和下一步。处理方式包括产品已有、客户配置、系统适配、产品缺口、暂不承诺；目前无法支持初步分类时可写待判断。比如“IT 说可以导出订单”可以记录为角色转述，尚不能证明已取得获准、完整、口径一致的数据。先对客户 A 练习一条完整记录，再写青禾自己的工作稿。

读 V03 第 11–13 页，先明确你正在考虑的**阶段**。客户 A 的候选阶段是小范围样本验证，开始前需要获准样本、明确口径、安排走查和投入；验证中才去学习名单质量、审核修改量与总耗时。对另一位客户，下一步可能只是资料核查或采购决定，所以不必一听到“AI 项目”就写“先试点”。

先独立回答 V03 第 14 页的三种条件变化，再看第 15–16 页：样本和责任都落实、有样本但范围冲突、样本和使用者都没有时，下一步应如何变化？每次都写明“为什么这样做”和“取得什么新证据后再调整”。最后浏览第 17–18 页，记下带到下一天的技术问题：缺时段如何澄清，金额由谁计算，覆盖由谁检查，客户数据和定义不同要改哪一层。

当天留下一份客户 A 的四问练习、一条 fit-gap 练习，以及青禾的独立初稿。把“课件说产品有这项能力”和“我已在本机实测”分开写；第二天重点学习判断方法，完整技术验证留给接下来两天。

## 第三天｜跟着一次请求读懂 Agent 怎样工作

V04 第 1–12 页先看一条明确时段的分析，再看“近期消费下降”这样缺时间的请求。读代码前先画一条自己预计的路线：用户输入→模型决定是否请求工具→程序检查工具名和参数→业务代码读取样例数据并计算→工具结果回给模型→输出回答。然后沿代码核对自己的路线。建议从工程的 product/system_prompt.txt、platform/fde_product/agent.py、business.py 和 interaction.py 找起；需要知道每一层负责什么，不必一上来逐行背代码。

理解几个关键分工。模型可以提出“比较消费”，但不能自行写 SQL 或授权一个时间范围。程序核对已确认日期、工具参数和角色；Business.compare 依产品语义计算净消费和下降人群。金额以分存储、按支付减退款计算，取消订单不计。样例中 M001、M004、M007 属于下降人群；S03 的 8 月未覆盖，未知不等于消费为零。结合 V04 第 33–34 页再比较 M004 的真实零、M005 的零基期和 M008 的覆盖未知。

V04 第 13–22 页再看 Agent 的状态图。model、tools、approval、execute 是不同步骤；SQLite checkpoint 保存会话，使任务可在澄清或确认之后继续。工具是否可见、JSON 能否解析、日期是否已确认、业务数据是否有效、最终答案是否引用了工具依据，是不同层的检查。用第 18 页的三条输入先自己猜会在哪层被拦，再到代码找对应位置。看到 completed，也要继续核对事实与建议；它表示一次任务状态，不能单凭这个词证明自然语言里的所有判断都准确。

V04 第 23–31 页看样例标签动作。这里的“动作”意味着独立 HTTP 服务上的状态可能发生变化，因此要先形成草案，再由人按当前草案明确确认，然后执行、查询、必要时撤销。你可以在教学 Mock 上做一次 M001 标签动作并核对 API 实际状态。拒绝旧草案后若改为 M004，应产生新的草案和确认；用户在聊天里说“我已批准”，不能让只读入口获得动作权限。若 HTTP 超时，保存原动作 ID 并查询状态，不能把“没收到回复”解释成“没执行”。

按第 32–39 页把客户扩展位置画成一张图：customer 放客户语义、提示词和业务工具，connectors 处理数据或 API 映射，evals 放客户评估断言，patches 只用于证明确有通用能力缺口后的补丁。青禾数据清洗和身份合并是后续学习任务；本周先认清扩展边界。最后比较两个词：Agent Harness 负责组织上下文、工具、状态与恢复；Eval Harness 负责用重复样本测量它的表现。

如果模型已配置，选一条自己的运行记录连接到代码路线；如果尚未配置，就把“代码可见的机制”和“本机未验证的行为”分开。当天的过程图应能让你在第四天看到失败时，知道先去哪个环节找证据。

## 第四天｜从一次运行记录找出问题最早发生在哪里

V05 第 1–3 页先讲“基线”。基线是固定条件下保存的一次真实结果，之后才能比较改动有没有用。记下所用模型与协议、产品版本、数据与语义版本、提示词、任务输入；成功和失败都保留。若同时换模型、数据和提示词，之后即使结果变好，也很难知道是哪项变化起作用。

按[工程 README](../../projects/fde-student-w01/README.md)配置自己的模型，先完成明确日期分析、缺时间澄清、S03 缺覆盖和只读拒绝。记录每次输入、工具参数、observations 中的结果、最终状态、trace ID 和证据路径。这里的 trace 可以理解为一次任务的“步骤账本”：同一个 trace ID 下能看到模型调用、工具和结果处理的先后。V05 第 4–5 页以 S03 返回 incomplete 为例，展示怎样沿步骤找到覆盖缺失发生的位置；程序把缺数据判为未完成，和模型自己说“未完成”并非一回事。

V05 第 6–10 页把故障分层。模型地址、网络、超时、响应格式属于接口层；无效参数和未确认日期先看工具与时间校验；日期或门店覆盖问题看业务层；工具结果正确但最终 JSON 不合法，则看输出处理；若 Promptfoo 断言脚本报 JavaScript 错误，先修评估脚本。一个具体例子：S03 没有 8 月覆盖，若模型生成“该店会员消费为零”，应先看工具是否已报告缺覆盖，再看最终回答在哪里丢掉了这个限制。不要靠加一句强硬提示词代替定位。

读第 11–12 页后，为一条真实失败写一个小实验：**观察是什么→第一次偏离发生在哪一步→你猜原因是什么→只改一处→保持哪些条件相同→重跑哪些正常和安全场景**。即使暂时没有修改，也可以记录下一步假设；只有做过前后对照，才能说某项调优有效。

V05 第 13–15 页讲基础评估。按 README 的先后顺序运行真实模型验证、Promptfoo，再让 finalize_evaluation.py 读取实际评估报告。打开报告时分三层看：评估程序本身能否运行，用例断言是否满足，原始回答是否真正有依据。一次平均分不能覆盖不安全或缺数据场景；课程的三个基础演示样例与 verify_product.py 的覆盖范围也不同。第 16 页把多余工具调用或澄清不足留作后续练习，先写清准备如何验证，再考虑改动。

当天保存真实模型基线、关键场景证据、一次有定位依据的诊断和评估报告。若模型接口尚未打通，记录脱敏错误和已尝试步骤，继续练习读取已有示范记录；示范记录注明来源，不写成自己的运行结果。

## 第五天｜从案例学习工作责任，再回到青禾访谈

V06 的 Morgan Stanley 案例帮助你理解一件事：AI 进入的是人的具体工作。先读课件第 1–5 页和[案例手册](<../../projects/W01 材料包 20261023/W01/案例手册/C01_Morgan_Stanley.md>)，分开画 Assistant 的内部知识使用与 Debrief 的会议后整理。对 Debrief 追问：会议内容在什么条件下进入系统？要点和行动项去哪里？邮件草稿由谁编辑并决定发送？这些去向决定了不同的交付责任。

再读 V06 第 6–9 页。对一个输出分别问三件事：**内容可用吗、约定流程完成了吗、实际工作改善了吗**。摘要正确，不自动证明 CRM 已写入正确对象；记录写入成功，也不自动证明顾问少花了时间。如果假设要自动发送邮件，就新增授权、确认与错发处理责任。课件中的访谈提纲和四问模拟是教师分析，不是企业当年的原始项目档案。你要迁移的是提问方法，不是这个案例的结果。

随后读 V07 第 1–12 页，把前四天手里的材料放回 W01 正式任务：样例导入、真实模型运行、基础评估、正式访谈、fit-gap 初步版、立项报告和预检。核对当前已有哪份自己的技术证据，哪份只是 README 预期，哪份还缺。V07 第 9 页说明本周只开放沈总，每周每角色正式访谈最多两次；访谈前先选能改变下一步决定的问题，避免把次数用于重复邮件内容。

可以先准备这样的追问方向，再根据沈总回答调整措辞和顺序：

| 想弄清什么 | 为什么值得问 |
| --- | --- |
| “三个月见效”具体看什么 | 决定验证目标与承诺边界 |
| “会员老化”依据是什么 | 决定是否围绕这个解释设计分析 |
| 小林现在如何得到名单和建议 | 决定产品应该进入哪项工作 |
| 谁提供数据、谁确认范围和投入 | 决定下一阶段是否具备开始条件 |

正式入口开放后保存原始问答和消息位置，整理时把沈总原话、自己的解释、已核实与仍未知分别写清。入口尚未开放，就先完成工程验证和访谈准备，正式访谈标为待完成。不能用课件回放补成真实访谈，也不能替老周、小林等角色写出他们没有说过的话。

正式访谈每周每角色最多两次；系统失败按页面规则返还次数，主动结束不返还。进入访谈前先写本次目的和最想解决的几项决策问题，结束后优先整理证据与新未知，再决定是否需要第二次。

最后把新取得的客户依据和产品证据汇到初步 fit-gap。分类和证据状态分开填写；能初步分类的据实分类，仍缺依据的保留待判断，并写出“谁提供什么、怎样验证、结果改变哪个判断”。本周不要求凑齐每一种分类或清空所有未知。

## 第六天｜比较两种进场起点，完成本周交付

V08 是教师团队探索投手 Copilot 早期产品共创的实录。先读第 1–15 页，比较有投手团队的服装客户与获客基础尚未建立的制造企业：同样听到“希望 AI 提效”，为什么适合投入的下一阶段不同？再读第 16–24 页，看产品方愿承担什么风险、双方后来约定了什么、能力验收与效率改善及广告效果分别需要什么证据、停止探索后还要怎样交接。注意“后来约定”不等于开始前已确定，“约定验收”不等于已验收。第 23–25 页首个用例尚未选定，下一步是观察投手的实际工作。

把 V08 与青禾列成两栏。V08 从产品方向尚在共创的起点出发；青禾是接手已有标准产品，须用能力矩阵、自己的运行和客户材料形成适配判断。可以借用“先确定要进入的阶段，再区分探索中可学习的问题与开始前必须满足的条件”的方法，不能直接借用共创商业条款、客户选择或阶段结论。

回看 V07 第 13–18 页和[作业任务书](<../../projects/W01 材料包 20261023/W01/05_作业任务书.md>)。把第一天的邮件理解、第二天的四问、第三四天的产品证据和第五天的访谈放到同一条证据链上。逐项修订青禾 fit-gap，再写立项报告：客户实际要改变什么，哪些话是角色转述，产品在样例中验证了什么，客户适配还缺什么，下一阶段先做什么、由谁提供条件、什么情况要调整或暂缓。报告所作承诺应与证据支持的范围一致。

正式产出物位于工程工作副本：artifacts/w01 下的 environment_check.json、model_baseline.json、runtime_evidence.json、product_fit_gap.json，以及 docs/w01/project_assessment.md。前三份 JSON 来自实际运行和验证，fit-gap 由填写稿及证据明细转换，报告由你依据材料写成。Promptfoo 结果、trace、其他引用证据与哈希也要保留。检查文件和版本后运行公开 checker，再对照真实行为与报告论证做人工复核；checker 通过只说明它负责的检查通过。

提交时按任务书把要求的文件和引用证据打成 zip。解压后顶层应看见 artifacts/、docs/ 等原路径；不要把虚拟环境、运行态或密钥装进去。保存 W01 版作为当时的证据快照。后续取得新资料时沿 GAP 编号修订，不把后来知道的事实改写成第一周已经知道。

这六天的顺序形成一条主线：先知道客户为什么提问题，再知道产品能如何帮忙，接着用运行记录核对能力，用访谈补足客户信息，最后作出可复核的阶段决定。若某项工作被模型服务或正式访谈入口挡住，就如实记录已完成部分、缺项和下一步补齐方式。
